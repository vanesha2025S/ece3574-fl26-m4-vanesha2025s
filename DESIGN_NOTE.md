# M4 Design Note

Due Wed Oct 28, 11:59 pm. See specification Section 7.

# 1. Components and Threads

I plan to keep MainWindow and all of the GUI widgets (WorkspaceWidget, SearchWidget with its SearchResultModel, TermInspectorWidget, and ContextWidget) on the main Qt thread. MainWindow's slots, corpus state changes, and decisions about whether to accept a finished build will all happen on this thread. The widgets will also only be created and updated on the main thread. Each corpus build will run in a separate `std::thread` managed by a BuildJob. The worker will use a copy of the Workspace documents, create a new ProcessingCore, apply the `--build-delay-ms` delay, and call `rebuild()`. The worker will not directly access widgets or MainWindow members. When the build finishes, it will notify MainWindow through `QMetaObject::invokeMethod` using `Qt::QueuedConnection`, so `build_finished(generation)` runs on the main thread. Search, Term Inspector, and Context will only use a corpus after MainWindow has accepted it.

# 2. Corpus States

I plan to use four corpus states: Not Built, Building, Current, and Failed. MainWindow will also keep a generation number that increases whenever the Workspace changes. The application starts in Not Built. When the user clicks Build Corpus from Not Built, Failed, or Current, the state changes to Building and a new job starts with the current generation number. If the build finishes successfully and its generation still matches, the state changes to Current and the chunk count is displayed. If the build throws an exception, the state changes to Failed and an error message is shown. Adding a document or clicking Reset increases the generation number and returns the state to Not Built. If an older build finishes after the Workspace has changed, its result will be removed without changing the current state. Search, Inspect, and Build Context will only be enabled when the corpus is Current, and Build Corpus will be disabled while Building.

# 3. Possible Problems and Solutions

One possible problem is adding a document while a corpus build is running. For example, suppose the generation number is 3 when the user clicks Build Corpus. Job A starts with generation 3 and a copy of two documents. While the worker is building, the user adds a third document. This increases the generation number to 4, changes the corpus state to Not Built, clears the previous outputs, and enables Build Corpus again. When Job A finishes, it sends `build_finished(3)` to MainWindow. MainWindow joins the completed thread and compares the generation numbers. Since 3 does not match 4, Job A's result is removed. The corpus stays Not Built, and Search remains disabled until a new build finishes.

Another problem is when the user clicks Reset while a build is still running. Reset clears the Workspace and increases the generation number, so the previous build becomes outdated. If the user adds new documents and starts another build before the first one finishes, both jobs may be running at the same time. However, only a result with the current generation number will be accepted. This prevents an older build from replacing the corpus for the new Workspace.

Exiting during a slow build is another situation I need to handle. If MainWindow immediately joins a thread that is still sleeping, the application could freeze while waiting. To avoid this, each BuildJob will have a `std::atomic<bool>` cancel flag. The build delay will be divided into smaller steps so the worker can check whether it should stop. For example, if the application is using `--build-delay-ms 5000` and the user clicks Exit while Job B is waiting, confirming Exit will end the Qt event loop. The MainWindow destructor will set Job B's cancel flag, allowing the worker to notice the cancellation and return without posting a result. MainWindow will then join the thread before destroying its members. This should allow the application to close without leaving any detached threads.

I also plan to handle build failures so the application does not remain stuck in the Building state. If `rebuild()` throws an exception, such as one caused by a duplicate document ID, the worker will catch it, store the error message, and notify MainWindow that the job has finished. MainWindow can then display the failure and change the state to Failed. If the failed job belongs to an older generation, the error will be ignored so it does not affect the current Workspace. The GUI should remain responsive because the build and delay happen on background threads. Completed jobs will be joined and removed when their completion notifications are handled, preventing finished threads from accumulating.

The only data that will be accessed by both threads at the same time is each job's cancellation flag. The main thread writes to it, and the worker reads it. Using `std::atomic` makes this safe. The worker will be responsible for writing its documents and build result, and MainWindow will only read the completed result after joining the worker thread.

# 4. Corpus Ownership

Each BuildJob will hold its temporary corpus using a `std::unique_ptr<ProcessingCore>`. The worker will create the ProcessingCore and populate it by calling `rebuild()`. MainWindow will own the jobs through a `std::vector<std::unique_ptr<BuildJob>>`, while the worker will be responsible for writing its own result. When MainWindow receives the completion notification, it will join the job's thread before accessing the completed corpus. If the generation number matches, the ProcessingCore will be moved into MainWindow and become the active corpus. If the generation number does not match, the result will be discarded automatically when the job is removed. The active corpus will also be destroyed when it is replaced by a newer build, cleared by Reset, or when MainWindow is destroyed. Using `std::unique_ptr` should make ownership clearer and avoid manually deleting objects.

### 5. Alternative Design

I considered joining the running worker whenever the user adds a document or clicks Reset. This would make sure only one build is running at a time and would simplify some of the state management. However, calling `join()` would force the main thread to wait for the build to finish, including any delay from `--build-delay-ms`. This could freeze the GUI and violate the responsiveness requirement in R1. Instead, I chose to give each build a generation number and discard outdated results. This allows the user to continue interacting with the application without the main thread waiting for an active build.
